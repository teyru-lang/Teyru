# W14 的量測紀錄：三條被排除的假路徑，與一張「還沒量到」的清單

這是一份**內部紀錄**（與 `scripts/lib-bytes-audit.md` 同性質），不是使用者文件。

**規則在 `AGENTS.md` 的量測那一組**；這裡是那條規則被換來的過程。這份文件存在的理由只有一個：**讓下一個人知道哪些路徑已經被量過、用什麼量的、以及哪裡還沒有證據**。最後那張清單是它最值錢的部分。

樹：`~/tywork/evalorder`，`v0.4.0` 之後的 main（`308c511` 與其前後）。編譯器 `teyru build -O2`，JDK `/opt/jdk21/jdk-21.0.11+10`。

## 方法（以及它怎麼錯了三次）

- 每個數字都是**交錯 A/B**：同一台機器、`taskset -c 3` 綁核、teyru 與 java 輪流、取最小。量的是**編譯好的執行檔**（AGENTS.md §6）。
- 量測期間 load 約 5、`nproc` 16。**小於約 2% 的差異不該被相信。**
- 我不用儀器化建置計時。`TEYRU_GCTRACE` 是既有開關，只在收集時多一次 `heap_used()`。

**這一輪三次因為「在一個不是那個程式的東西上量它」而得到錯結論**，每次都靠「數字與真品矛盾」抓出來：

1. `bench_alloc` 被當成配置器基準 —— 它 **0 次收集**（`Cell` 不逃逸，產生器早就配置在堆疊上）。
2. C 微基準把 `ty_rem_int` 標成 `noinline` 來「定價一次呼叫」，於是量到 47% —— 但**真品的 `-O2` 是整程式 LTO 建置，那個呼叫早就沒有了**（`nm` 找不到符號）。
3. replica 被 clang **向量化**（66 條指令裡 58 條 vector），於是「拿掉什麼都量到 0」是假象 —— 真品的迴圈是純量、24 條指令。

**規則：replica 與真品不一致時，先假設 replica 錯。**

## 一、配置器：`bench_alloc` 不是它的基準

`TEYRU_GCTRACE=1` 在 scale 800000000 下 **0 次收集**。所以 `bench_alloc` 的 0.14× 不是「配置器慢 7 倍」，是「800M 次堆疊槽初始化＋虛擬呼叫」對上「JVM 把整支程式消掉」。

真正會配置的：

| 程式 | wall | 收集次數 | 總 pause | pause 占比 |
|---|---|---|---|---|
| `bench_string 16000000` | 1.07s | 633 | 89.5ms | **8.4%** |
| `bench_invoke 100000000` | 2.07s | 1525 | 347.2ms | **16.8%** |

每次 pause 0.25–0.6 ms、`live=10kB`。**收集本身不是瓶頸。**

**順帶發現**：裝箱走的是**前奏方法呼叫**（`M_teyru_Integer_valueOf_0`），不是 runtime helper——每次裝箱是「一次呼叫＋一次 `ty_alloc`＋一次欄位寫入」。**沒有把兩者分開量。**

### 排除的路徑

- **「配置器的快路徑／慢路徑／批次需要優化」** —— 未量到證據。fast/slow/batch/鎖取得的分解要有 `tyrt.c` 的計數器（AGENTS.md §10 那一輪的儀器化建置**不在樹上**），我沒有重建它。**這是一條還沒量到的路徑，不是排除。**

## 二、介面呼叫：`bench_oop` 0.43× 幾乎全是「呼叫沒變成直接呼叫」

同一份工作量的三個降階（`oop_vtable.teyru`／`oop_direct.teyru`）：

| 變體 | 呼叫怎麼降 | 500000 rounds |
|---|---|---|
| `bench_oop` 原樣 | `ty_itab()` ＋間接呼叫 | **0.91s** |
| vtable（`abstract class`） | `obj.cls->vtable[7]` ＋間接呼叫 | **0.77s** |
| 直接呼叫（`area()` 改 `final`） | 直接呼叫 | **0.33s** |
| *（對照組）* JVM | JIT | **0.39s** |

- **itab 走訪 = 0.14s（15%）**、每次呼叫 0.28 ns；
- **分派本身（vtable 載入＋間接呼叫／不能 inline）= 0.44s（48%）**、每次 0.88 ns；
- **剩下的 0.33s 是真正的工作，比 JVM 的 0.39s 還快。**

所以 `bench_oop` 的問題**不是介面特有的東西**，是熱呼叫點沒有變成可 inline 的直接呼叫。

### 排除的路徑

- **「單型 inline cache」** —— **對 `bench_oop` 可能反而更慢**：它的陣列是 Rect/Square **交替**，單型守衛會**每次都失敗**。**未實作、未量。**
- **itab 結果快取** —— 上限 **≤15%**（0.91 → 0.77），換一個新快取結構不划算，**先不做**。

## 三、安全點輪詢：**量不到**，而且 `bench_loop` 的 0.87× 不是它

- 沒有稀釋的迴圈（`total += buf[i & 1023]`、10 億圈）：**有輪詢 0.219s／沒有 0.218s** ⇒ 每次約 **1–3 皮秒**。`ty_safepoint` 是一次 acquire 載入（x86 上就是普通載入）＋幾乎不跳的分支。
- 純量受控實驗裡再確認一次：拿掉輪詢 **0%**。

### 排除的路徑

- **「更便宜的安全點」** —— **收益 0**。

## 四、`bench_loop` 那 14%：四個嫌疑逐項量到 0，剩下的不在產生器

真品 `-O2` 的熱迴圈（`objdump`，24 條指令、**純量**、`% 7` **已經**被折成 `imul $0xffffffff92492493` ＋ `shr`／`sar`）：

```asm
4039d0:  mov  ty_stw_request(%rip),%eax   ; 安全點輪詢
4039d6:  test %eax,%eax
4039d8:  je   4039df
4039da:  call ty_safepoint_slow
4039df:  mov  0x8(%r14),%rsi              ; 每一圈重新載入 xs->len
4039e6:  jle  403be6
4039ec:  mov  0x10(%r14),%rax             ; 每一圈重新載入 xs->data
4039f0:  movslq (%rax,%r12,4),%rax
4039f4:  imul $0xffffffff92492493,%rax,%rcx
...
403a19:  add  %rax,%r15
403a1c:  inc  %r12
403a1f:  cmp  $0x400,%r12
403a26:  jne  4039d0
```

受控實驗（**純量**、`#pragma clang loop vectorize(disable) unroll(disable)`、10 億圈、綁核、取三次最小、旗標與驅動程式一致）：

| 變體 | 時間 |
|---|---|
| A3 產生器的形狀 | **1.008–1.015s** |
| B3 把 `len`／`data` 綁進區域變數 | 1.027–1.030s |
| C3 B3 再拿掉安全點輪詢 | 1.029–1.036s |
| D3 拿掉 `total` 的 lvalue 暫時指標 | 1.023–1.032s |
| E3 **加上**計數器的 lvalue 暫時指標 | **1.005–1.009s** |

**每一個都是 0（在 ±2% 噪音內）**——包括兩個 lvalue 暫時指標（加上它反而略快，方向都不一致）。

組語旁證：同一個檔案裡，純量迴圈的 A3 是 40 條、B3／C3 是 16 條，而**每個被數到的迴圈裡標頭重載都是 0 次**——在純量迴圈裡 **clang 自己就把標頭載入提出去了**。真品那兩條重載是**被 LTO inline 成 3010 條指令的大函式**的結果，不是「產生器沒綁標頭」。

### 一個被論證擋下來的最佳化（沒有實作）

「把熱迴圈的 `len`／`data` 綁進區域變數」**最直覺的版本不健全**：把 null 檢查與標頭載入一起提到迴圈外，會改變可觀察行為。JDK 是裁判：

```java
int[] xs = null; int n = 0;
for (int i = 0; i < n; i++) { System.out.println(xs[i]); }   // loop not entered: NO NPE
for (int i = 0; i < 1; i++) { System.out.println(xs[i]); }   // loop entered: NPE
```

**迴圈沒被進入時 Java 不丟 NPE。** 而載入 `n->len`／`n->data` 要求 `n` 非 null，所以檢查與載入**只能一起提**，一起提就不健全。健全版本需要新條件「**迴圈保證至少執行一次**」（`for (k = 0; k < C; k++)`、`C` 是編譯期常數 > 0，再加上參考是區域變數或參數且迴圈內無賦值）——**那是新的分析**，而上面的數字說**不值得**（0% < 10% 的門檻），所以**沒有實作**。

### 已排除／未解釋

- **排除**：除數呼叫（`-O2` 已被 LTO 消掉 ✓）、安全點（0 ✓）、標頭重載（0 ✓）、兩個 lvalue 暫時指標（0 ✓）。
- **未解釋**：真品 1.16s 對純量 replica 1.001s 的 **14%**。嫌疑是那個大函式本身（**code layout／LTO 後的暫存器壓力**），**不是**任何單一項產生器包在迴圈上的東西。**沒有繼續追。**
- 這一輪因此**沒有**在 `bench_loop` 的 0.87× 上找到任何可歸給產生器的 ≥10% 項目。**這是答案，不是放棄。**

## 沒量到、沒確定（下一個人從這裡開始）

1. **配置器的 fast/slow/batch/鎖取得分解** —— 要儀器化建置，樹上沒有。
2. **裝箱的「呼叫」與「配置」分開定價** —— 已知它是一次前奏呼叫，兩者沒有分開量。
3. **單型／多型守衛的實際收益** —— 未實作，而 `bench_oop` 是雙型，單型守衛會每次失敗。
4. **純量環境下的 lvalue 暫時指標** —— 這一輪量了（0 ✓），但**只在 `bench_loop` 這個形狀上**；別的形状沒有。
5. **`bench_string` 剩下 91.6% 的分解** —— 只量到收集占 8.4%。
6. **一支真正會逃逸的配置基準** —— `bench_alloc` 被逃逸分析變成堆疊配置，**這一輪沒有替代品**。
7. **真品與純量 replica 那 14%** —— 嫌疑在大函式本身，未證。
8. **安全點對停止世界延遲上限的影響** —— 只量了吞吐成本（0），沒有量延遲上限。
9. **物件標頭與大小** —— `new Object()` 是 **32 位元組**（8 的 payload ＋ 16 的標頭，對齊後 32），
   Java 是 **16** —— 也就是每個物件**兩倍的記憶體流量**。這是 `bench_invoke` 那一項的**主要槓桿**
   （AGENTS.md §10：**不是比較次數，也不是反射**）。**還沒量到的**：那 16 個標頭位元組**各是什麼**、
   其中哪些可以搬走或縮小、以及在**真的會逃逸的基準上**（見第 6 項）收窄 8 或 16 位元組各值多少。

## 五、後續補記：`bench_oop` 的重測，與「裝箱快路徑」的決定

這一節是上面那份清單開始被消費之後補上的，兩件事都已**結案**，一件**沒有實作**。

### `bench_oop`：重測完成，結論與第一輪一致

三種分派降階（同一份工作量）在 500000 rounds 上重測，數字與第一輪相符：

| 變體 | 呼叫怎麼降 | 時間 |
|---|---|---|
| `bench_oop` 原樣 | `ty_itab()` ＋間接呼叫 | 0.91s |
| vtable（`abstract class`） | `obj.cls->vtable[7]` ＋間接呼叫 | 0.77s |
| 直接呼叫（`area()` 改 `final`） | 直接呼叫 | **0.33s** |
| *（對照組）* JVM | JIT | 0.39s |

**真正的工作（0.33s）已經比 JVM 的 0.39s 快** —— 輸的是**熱呼叫點沒有變成可 inline 的直接呼叫**（48%）。

**決定（不實作）**：

- **單型 inline cache —— 不做。** `bench_oop` 的陣列是 Rect/Square **交替**，
  單型守衛會**每次都失敗**；它會把 15% 的 itab 成本換成一次守衛失敗的代價。
- **itab 結果快取 —— 不做。** 上限 **≤15%**（0.91 → 0.77），換一個新快取結構不划算。
- **兩者都不是「介面特有的東西」** —— 它是「這個熱呼叫點不能 inline」，那是**另一個題目**，
  不在這一輪的範圍裡，也**沒有**被這一份排除。

### 裝箱快路徑：**不做** —— 而且理由是「槓桿不在那裡」

清單第 2 項（「裝箱的『呼叫』與『配置』分開定價」）已經被量到了，數字在 `AGENTS.md` §10：

- 一次 `bench_invoke` 迴圈（20M 次）約 **27 ns／次**；其中**兩次裝箱約 19 ns ＝三分之二**；
- 而快速路徑本身只要約 **2 ns**（標頭寫入 0.5、payload 歸零 0.23、預算檢查 0.27、執行緒指標 0.06）；
- **真正貴的不是「多一次呼叫」，也不是「比較次數」，是物件的大小**：
  Teyru 的 `new Object()` 是 **32 位元組**（8 payload ＋ 16 標頭，對齊後 32），Java 是 **16** ——
  **每個物件兩倍的記憶體流量**。

**決定：不做「裝箱快路徑」。** 理由是它打不到槓桿：
任何**仍然配置一個 32 位元組箱子**的捷徑（少一次前奏呼叫、少一次欄位寫入、小整數快取之外的任何做法），
都要付那兩倍的記憶體流量；反之，若箱子變小，**所有**配置都受益，不必特別處理裝箱。
**所以要動的是標頭／大小，不是裝箱那條路徑** —— 那是清單新增的第 9 項。
